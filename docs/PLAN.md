เอกสารนี้บันทึกว่าโจทย์คืออะไร วางแผนแก้อย่างไร ทำอะไรเสร็จแล้ว และเหลืออะไรต่อ

## 1. โจทย์และข้อกำหนด

ผู้ใช้เป็นคนไทยที่อ่านหนังสือ/บทความภาษาอังกฤษ (ทั้งบนหน้าเว็บและไฟล์ PDF) ระดับภาษาอังกฤษพื้นฐาน
ปัญหาที่ระบุไว้:

1. ต้องคัดลอกคำไปเปิด Google ทีละคำ → เสียเวลา
2. คำที่เคยแปลแล้วลืม เพราะไม่มีคลังเก็บ ไม่มีประวัติ
3. ดูคำแปลแล้วไม่เข้าใจ เพราะไม่รู้ว่าตรงกับบริบทไหน ไม่มีภาพเชื่อมโยงให้จำ

ความต้องการที่ระบุชัด:

## 2. การตัดสินใจเชิงสถาปัตยกรรม

### 2.1 ทำไมเลือก Chrome Extension เป็นแกนหลัก (ไม่ใช่ Windows Desktop)

- ตรงกับพฤติกรรม "อ่านในเบราว์เซอร์" และเข้าถึง DOM ได้ตรง ๆ ทำให้ดับเบิลคลิก/คลุมข้อความทำได้แม่นยำ
- ไม่ต้องติดตั้งอะไรเพิ่ม ติดตั้งผ่าน `chrome://extensions` ได้ทันที
- **ข้อจำกัดสำคัญที่ต้องแก้:** Chrome แสดง PDF ด้วยปลั๊กอินภายใน (`mhjfbmdgcfjbbpaeojofohoefgiehjai`)
  ซึ่ง content script ของส่วนขยายอื่นเข้าไปไม่ถึง → จึงต้อง **ฝัง pdf.js ไว้ในส่วนขยายเอง**
  แล้วเปลี่ยนเส้นทางไฟล์ `.pdf` มาที่ตัวอ่านของเรา (`webRequest.onHeadersReceived` + `webNavigation.onCommitted`)
- สำหรับโปรแกรมอ่าน PDF นอกเบราว์เซอร์ (Adobe/Foxit/Word) ส่วนขยายช่วยไม่ได้ →
  เสริมด้วยสคริปต์ PowerShell ที่ใช้คีย์ลัดระดับระบบ (`desktop/TranslatePopup.ps1`)

### 2.2 ทำไมทุกการเรียกเครือข่ายต้องผ่าน service worker

ตั้งแต่ Chrome 85 content script ถูกบังคับด้วย CORS ของหน้าเว็บนั้น ๆ
ดังนั้นการเรียก API แปลทั้งหมดจึงรวมศูนย์ที่ service worker (ซึ่งมี host permission `<all_urls>`
และไม่ติด CORS) แล้วส่งผลลัพธ์กลับให้หน้าเว็บ — ได้ประโยชน์เพิ่มคือ **แคชรวมศูนย์** และ**คีย์ API ไม่ต้องอยู่ในหน้าเว็บ**

### 2.3 ทำไมออกแบบเป็น "ท่อ" หลายชั้น (layered pipeline)

Google Translate แบบไม่เป็นทางการถูกจำกัดการใช้งานเป็นครั้งคราว (ทดสอบแล้วเจอ HTTP 200 ที่เป็นหน้า
"Sorry..." จากระบบป้องกันการใช้งานอัตโนมัติ) จึงออกแบบให้:

```
ผู้ใช้เลือกข้อความ
      │
      ├─ ตรวจแคช (chrome.storage.local)  ──► เจอ = ตอบทันที
      │
      ├─ ชั้นที่ 1: ผู้ให้บริการแปล  (Google → Google Dict → MyMemory → Libre → DeepL)
      │              ล้มเหลวทีละเจ้าจนกว่าจะได้ผล (บันทึกเหตุผลไว้ใน warnings)
      │
      ├─ ชั้นที่ 2: ข้อมูลเสริม (ขนานกัน)
      │              Datamuse (คำพ้อง+ความถี่+นิยาม) · Tatoeba (ตัวอย่าง+คำแปลไทย) · Wiktionary (ชนิดคำ+นิยาม)
      │
      ├─ ชั้นที่ 3: AI (ถ้าเปิด) — แปลตามบริบท + อธิบาย + ตัวอย่างเหตุการณ์ + ตัวช่วยจำ
      │
      └─ รวมผล + จัดลำดับ + แคช + (บันทึกอัตโนมัติถ้าเปิด)
```

จุดสำคัญ: **ทุกชั้นพังได้โดยไม่ทำให้ทั้งระบบพัง** ถ้าไม่มี AI ก็ยังได้คำแปล + คำพ้อง + ตัวอย่าง;
ถ้า Google ถูกจำกัดก็ยังมี MyMemory

### 2.4 "ตัวอย่างที่ตรงบริบทที่สุด" คือประโยคที่ผู้ใช้กำลังอ่าน

ผู้ใช้อ่านหนังสือจริงอยู่แล้ว ประโยคนั้นจึงเป็นตัวอย่างที่ดีที่สุด และทำให้เห็นว่าคำนี้ใช้ในบริบทไหน
ระบบจึงดึงประโยคที่ครอบคำเป้าหมายจากย่อหน้าที่อ่านอยู่ แปลเป็นไทย แล้ววางเป็นตัวอย่างลำดับแรกเสมอ
(ทำได้แม้ไม่เปิด AI — ต่างจากคู่แข่งที่ต้องพึ่ง AI เท่านั้น)

### 2.5 คำพ้องต้อง "ง่าย" จริง ไม่ใช่แค่คำพ้อง

ใช้ความถี่การใช้คำจริงจาก Datamuse (`f:` tag) จัดเป็น 3 ระดับ
- `f ≥ 10` → **ง่าย/ใช้บ่อย** (เช่น live, elastic)
- `f ≥ 1` → ทั่วไป
- `f < 1` → ทางการ (ถูกกรองออกเมื่อมีตัวเลือกง่ายพอ)

พร้อมกรองคำที่ซ้ำกับคำตั้งต้น และให้ AI ช่วยอธิบายความต่างของแต่ละคำ (`note`)

### 2.6 เก็บข้อมูลในเครื่อง 100%

ไม่มี backend เลย: คลังคำศัพท์อยู่ใน IndexedDB, ตั้งค่า/แคช/API key อยู่ใน `chrome.storage.local`
ทำให้ไม่มีค่าใช้จ่ายในการรัน ไม่มีปัญหาความเป็นส่วนตัว และไม่ต้องมีบัญชีผู้ใช้

### 4.4 บั๊กจริงที่การทดสอบจับได้ (และแก้แล้ว)

| บั๊ก | อาการ | การแก้ |
| --- | --- | --- |
| CSS `display` ทับ attribute `hidden` | overlay ที่ซ่อนอยู่ยังบล็อกการคลิกทั้งหน้า (กดปุ่มบน toolbar ไม่ได้) | เพิ่ม `[hidden] { display: none !important; }` |
| ตีความโครงสร้าง Google ผิด | เอา "คำแปล" มาแสดงเป็น "ความหมาย" ซ้ำหลายบรรทัด | ตรวจ payload จริงแล้วเขียน parser ใหม่ (entry[2] = พจนานุกรมย้อนกลับ ไม่ใช่นิยาม) |
| คำพ้องมีคำตั้งต้นปนมา | "resilient" ปรากฏอยู่ในรายการคำพ้องของตัวเอง | กรองคำที่ตรงกับคำค้น |
| บริบทกว้างเกินไป | ตัวอย่างประโยคลากทั้งหน้า (ติดหัวเรื่องเข้ามาด้วย) | หยุดเก็บบริบทที่บล็อกระดับย่อหน้า (`P`, `LI`, `TD`, …) |
| บริบทใน PDF ติดคำกัน | ข้อความจาก text layer ต่อกันไม่มีช่องว่าง | รวมเฉพาะ span ที่อยู่บรรทัดเดียวกัน |
| คำแปลไทยของคำพ้องกำกวม | แปลคำเดี่ยว ๆ แล้วได้ความหมายผิดบริบท | แปลเฉพาะคำระดับง่าย-กลาง ไม่แปลคำจาก reverse dictionary และตรวจผลลัพธ์ก่อนใช้ |
| ฟังก์ชันสร้างไอคอนคืนค่าผิดชนิด | ไฟล์ไอคอนกลายเป็นพิกเซลดิบ (147 KB) ไม่ใช่ PNG — เบราว์เซอร์แสดงไม่ได้ | ห่อด้วย `encodePng()` ก่อนเขียนไฟล์ (ทดสอบจับได้เพราะตรวจ magic bytes ของ PNG) |
| แทนที่ข้อความจน element หาย | หน้าแสดงเวอร์ชันว่างเปล่า เพราะเขียนทับ `textContent` ของ container ที่มี `<span id="version">` อยู่ข้างใน | แยก span ของคำนำหน้าออกมา แล้วแก้เฉพาะ span นั้น |
| DeepL ยังแสดงบนเว็บแอป | ผู้ใช้ตั้งค่าแล้วทดสอบไม่ได้ เพราะ DeepL ไม่มี CORS | ติดธง `extOnly` ให้ผู้ให้บริการ/ช่องตั้งค่าที่ใช้ได้เฉพาะส่วนขยาย |
| Tatoeba ตัวเก่าทำให้คอนโซลเต็มไปด้วย error CORS | หลัง API ใหม่ตอบแล้วไม่พบประโยค ระบบยังลอง API เดิมที่ไม่มี CORS | ถ้า API ใหม่ตอบสำเร็จแล้วไม่พบผลลัพธ์ ให้หยุด ไม่ต้องลองตัวเก่า |
| คำเดียวที่ไม่มีบริบทไม่มีตัวอย่างประโยคเลย | บนมือถือผู้ใช้แชร์คำเดียวมา จึงไม่มีประโยคให้ใช้เป็นตัวอย่าง | ถ้าไม่พบตัวอย่างเลย ให้ค้นประโยคจริงของ "คำพ้อง" มาประกอบ แล้วติดป้ายกำกับว่าเป็นคำอื่น |

## 5. งานต่อไป (roadmap)

**น่าสนใจและต่อยอดได้ทันที**

- [ ] OCR สำหรับ PDF ที่เป็นภาพสแกน (เช่น Tesseract.js) แล้วให้เลือกคำได้เหมือน PDF ปกติ
- [ ] โหมดอ่านแบบ "คำศัพท์ที่ควรรู้ในหน้านี้" — สแกนหน้าเว็บ/หน้า PDF แล้วไฮไลต์คำที่อยู่นอกคลังคำของผู้ใช้
- [ ] ประมาณระดับคำศัพท์ (CEFR A1–C2) เพื่อกรองคำที่ง่ายเกินไปออก
- [ ] **ซิงก์คลังคำระหว่างคอมกับมือถือแบบอัตโนมัติ** (ตอนนี้ใช้ส่งออก/นำเข้า JSON) — เช่นผ่านโฟลเดอร์ที่ผู้ใช้เลือกเอง หรือ WebDAV ที่ผู้ใช้ตั้งเอง เพื่อไม่ต้องมีเซิร์ฟเวอร์กลาง
- [ ] บัตรคำแบบพิมพ์ได้ + นำออกเป็น APKG (Anki) โดยตรง
- [ ] รองรับ Firefox (ต้องใช้ `browser.*` + ปรับ manifest และเลี่ยง `webRequest` แบบที่ใช้อยู่)
- [ ] **แชร์เป็นรูปภาพ/ข้อความออกไป** จากหน้าคำแปล (เช่นส่งเข้าห้องแชทให้เพื่อน)
- [ ] ปุ่มลัดบนหน้าจอโฮมของ Android (long-press ไอคอน → แปลจากคลิปบอร์ด) — manifest มี `shortcuts` ไว้แล้ว
- [ ] Widget/Quick Settings tile สำหรับแปลจากคลิปบอร์ดในแตะเดียว (ต้องทำเป็นแอปเนทีฟ)

**ปรับปรุงคุณภาพ**

- [ ] แคชผลลัพธ์แบบ semantic (คำที่รากเดียวกันใช้ผลร่วมกันได้)
- [ ] ให้ผู้ใช้เลือก "โทนคำแปล" (ทางการ/กันเอง) ต่อเว็บไซต์
- [ ] แสดงกราฟความคืบหน้าการทบทวน (จำนวนคำที่จำได้ระยะยาว, streak)
- [ ] รองรับหลายภาษาต้นทางพร้อมกันในหน้าเดียว (ตอนนี้อิงการตรวจจับอัตโนมัติ)

**ข้อควรระวังหากจะทำต่อ**

- Google Translate แบบไม่เป็นทางการไม่มีการรับประกันความเสถียร — ควรมีผู้ให้บริการสำรองเสมอ
- ถ้าจะขึ้น Chrome Web Store ต้องเตรียม privacy policy (ระบุว่าส่งข้อความไปยังผู้ให้บริการแปล/AI)
  และตรวจว่าการใช้ endpoint ไม่เป็นทางการสอดคล้องกับนโยบายร้านค้า
- ฝั่งมือถือ: PWA ต้องติดตั้งก่อน Share Sheet จึงจะทำงาน และ DeepL/Ollama ใช้ไม่ได้ (ข้อจำกัดของเบราว์เซอร์ ไม่ใช่ของโค้ด)
  ถ้าต้องการฟีเจอร์เหล่านั้นบนมือถือจริง ๆ ต้องทำแอปเนทีฟ (เช่น Flutter) ซึ่งแลกมาด้วยการดูแลโค้ดสองชุด —
  ทางที่เลือกจึงเป็นการใช้โค้ดชุดเดียวแล้วประกอบเป็นสองแอป เพื่อไม่ต้องแก้ไขซ้ำสองที่
